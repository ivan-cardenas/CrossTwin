**physicalEnv** — `RS_Imagery -> LandCover` is partial: the land-cover classes are still plain imports, but a Sentinel-2 broadband albedo raster (`sentinel2_albedo_raster`, openEO `ALBEDO`, Bonafoni & Sekertekin 2020 coefficients in `physicalEnv/calculations/albedo.py::ALBEDO_COEFFICIENTS`) is stored as each polygon's `albedo` (zonal mean, `albedo.measure`, receiver `albedo_imagery_saved` ← `SatelliteImagery` with index ALBEDO; the land-cover bulk finalizer runs `measure_missing`). Polygons without a measurement fall back to their `material`, set from the class's `default_material` (keyword table `albedo.CLASS_MATERIALS` of material codes). `SurfaceMaterialProperties` holds Table 5.1 of Oke et al. (2017) *Urban Climates* (45 surfaces, seeded by migration 0013: `code`, `category` (bare ground, low vegetation, forests, water, snow/ice, roads, walls, roofs, windows, paints, metals, urban areas), `albedo_min`/`albedo_max`, `albedo` = the table's average else the midpoint, `note`, `source`; thermal fields nullable). The material FKs offer only the categories that fit them (`limit_choices_to` = `physicalEnv.models.land_cover_materials` / `roof_materials` / `street_materials`, `MATERIAL_CATEGORIES_FOR`), in the map editor's selects and the admin; the file-upload importer resolves a material by code, name or `Category: Name` (`SurfaceMaterialProperties.lookup`, called by `importer/views.py::_resolve_fk` for any model with a `lookup` classmethod); `LandCoverVector.effective_albedo` picks one. A geometry change drops the measured value; editor building rings get a roof + paving estimate (`albedo.ring_albedo`). Nothing reads albedo yet (SOLWEIG uses its own UMEP class albedo). `New_Green_Area -> LandCover` is implemented: a green space (`nature.GreenSpaces`; a park is a green space of `type` `park`) drawn or reshaped in the map editor (`is_editor_change()`; receivers `green_space_saved`/`green_space_deleted`) turns its outline into *Green urban areas* (`landcover.green_area`, grass or tree material), released on move/delete (`release_green_area`); the cut/release code is shared with the building ring (`convert_area`, `release_owner`, `Owner`; cuts carry `owner_building` or `owner_park`, a check constraint keeps exactly one). (`RS_Imagery/LandCover -> LST` is implemented, see urban_heat). `LandCover/Soil_Type -> Infiltration` is implemented as a dashboard indicator (SCS Curve Number for a rain event, `physicalEnv/calculations/soil.py`, see below) and stored on each `watersupply.AvailableFreshWater`: its `save()` takes the soil x land-cover pieces of its polygon (`soil_landcover_composition`, wet-season groundwater) and derives `infiltrationRate_cm_h` (`soil.weighted_infiltration_rate_mm_h`: mid-range final rate of each piece's soil group x its unsealed share, `IMPERVIOUS_FRACTIONS`; roads/rail 0.6 is an estimate) and, with a year of daily KNMI rain and Makkink reference ET at the nearest station (`weather/calculations/water_balance.py::yearly_water_balance`, ≥ 360 days; `recharge_year` pins a year, else the latest complete one), `infiltrationDepth_cm` (`watersupply/calculations/chain.py::recharge_depth_cm_yr`: ΣP − Σ per-piece daily SCS runoff − ET, ≥ 0; crop factor 1, no soil-moisture store), then `yield_Mm3_year` = depth / 100 x area / 1e6 (`chain.recharge_Mm3_yr`). This implements `Infiltration -> Available_FW` and `Meteorology -> Available_FW`. A missing input keeps the stored (or supplied) value. The daily rows come from the catalog entry `knmi_daily_water_balance` (`weather/knmi.py`: daggegevens.knmi.nl `RH`/`EV24` plus the day's mean wind `FG`, temperature `TG`, global radiation `Q` (as 24 h mean W/m²), humidity `UG` and vapour pressure derived from `TG`/`UG` (`daily_values`; KNMI has no daily vapour pressure; rows tagged `period = 'day'`, everything else defaults to `'hour'`), no key, stations within 25 km of the bbox, `Meteorology` at noon UTC with `reference_et_mm`, `WeatherStation.knmi_id`; `parse_knmi` is shared with the SOLWEIG hourly fetch). Receivers in `watersupply/signals.py` (`refresh_freshwater`, deferred by `deferred_water_refresh`) re-save the sources over a changed `SoilArea`/`LandCoverVector`/`GroundwaterDepth`/`SoilType`, editor-written land cover (`landcover_created`), a daily `Meteorology` row, or a bulk daily import (`weather.knmi.daily_water_balance_changed`); the importer's bulk finalizers for `LandCoverVector`/`SoilArea` replay them. `totalQuantity_Mm3` (the stock) stays a flat input. `New_Units -> LandCover` is implemented. Stored, for buildings drawn in the map editor (negative id): `physicalEnv.signals.building_created` → `physicalEnv/calculations/landcover.py::urbanize_around` cuts a 10 m buffer (clipped to the city) out of the city's latest-year `LandCoverVector` polygons and inserts it as one "urban fabric" polygon tagged `source_building`; each cut piece is kept as an `UrbanFabricCut` (with the source polygon's id and attributes; `registry_hidden = True` keeps it out of the model registries). Moving (footprint changed; `pre_save` stashes the stored one) or deleting (`building_deleted`, skipped while `core.editing.is_restoring()`) the building runs `release_ring`: pieces go back to their polygons (only what the ring still holds; swallowed polygons are recreated with their id), cuts that later rings took from this ring are re-targeted to its targets, then the ring and its cuts are deleted. BAG imports never trigger it; rings from before `source_building` existed can't be released. `Buildings -> DSM` is implemented as an overlay (`physicalEnv/calculations/dsm_patches.py`): a building the map editor creates, reshapes, re-heights or deletes (`core.editing.is_editor_change()`; imports never) gets one `DSMBuildingPatch` (original footprint, current footprint, height = `height_m`, else 3 m per floor), applied by `svf.load_dsm` to every DSM window read for analysis (original footprint → ground, current footprint → median ground + height; ground = DEM on the same grid, else a 40 m minimum filter of the DSM). The measured DSM COG (`cog_path`) is never rewritten; the map shows `DigitalSurfaceModel.edited_cog_path`, a copy with the patches burnt in (`physicalEnv/calculations/dsm_edited.py`): `dsm_patch_changed` queues a refresh on commit for a background worker thread (`core/background.py::BackgroundWorker`, one per process, coalesces edits; `DSM_EDIT_BACKGROUND = False` in `settings_test` runs it inline), whose `refresh_pending` recomputes each new `DSMEdit` area as measured COG + all patches, warps the changed cells back onto the COG grid and writes a new versioned COG (`edited_upto` = last DSMEdit written; a new `cog_path` rebuilds it from all patches); `core/views.py::displayed_cog_path` serves it and after `feature-saved`/`backup-restored` `Layers.js::refreshDsmAfterEdit` polls `/physicalEnv/dsm/edited/status/` (`busy()`) and then reloads the DSM tiles. The rewrite is GDAL compression + overviews (CPU, `NUM_THREADS=ALL_CPUS`); a GPU does not help it. Patches are journalled (`dsm_patch_rewriting`/`dsm_patch_created`, `mainMap/signals.py`) so Restore reverts them; every patch change, Restore included, appends a `DSMEdit` (area + time), and SVF rasters / SOLWEIG runs older than an overlapping edit are reported as stale (`urban_heat/solweig/pipeline.py::stale_results`). `Vegetation_Coverage -> DSM` is implemented the same way: a `nature.Tree` or `nature.Forests` row the editor creates, moves, resizes or deletes gets one `DSMVegetationPatch` (`record_vegetation_change`). `apply_patches` runs building originals → ground, then tall vegetation (> `MIN_CANOPY_M`, outside stored footprints) within `TREE_CLEARANCE_M` 10 m of a new or moved building footprint → ground (`clearance_zone`; a height-only change keeps the trees; the patch lookup and `DSMEdit` area are padded by the same 10 m), then vegetation cleared (a tree's whole old crown, a forest's lost area; only cells more than `MIN_CANOPY_M` 2.5 m above ground and outside stored building footprints), then vegetation added (a tree: paraboloid crown of `height_m`, default 10 m, crown `crownDiameter_m` else 0.6 × height; a forest's gained area: flat 15 m, `max` with the DSM), then current buildings raised. Green spaces (parks included) are not sources (their outlines don't record trees). Vegetation patches use the same `dsm_patch_rewriting`/`dsm_patch_created` journal signals and `DSMEdit` log. Dashboard, for the housing pipeline: `housing/calculations/indicators.py::calculate_pipeline_land_take` intersects pipeline project footprints with the latest land cover (greenfield vs infill ha) and writes nothing.

**urban_heat** — Climate scenario runs (2026-11-16): creating a `weather.ClimateScenarioRun` (Scenarios panel, staff) makes `urban_heat/signals.py` store a `ScenarioHeat` (observed hour of KNMI/ERA5 + the same hour moved into the scenario: `climate.apply_to_weather`, `apply_to_day_values`) and queue one SOLWEIG run on the shifted hour (`urban_heat/solweig/scenario.py`, the one post_save that starts GPU work; never on re-save; the current values come from an observed run of the same hour covering the view, `find_baseline`, else stay empty) tagged `climate_run`, which also store WBGT from Tmrt (`urban_heat/calculations/chain.py::wbgt_outdoor_c`, ISO 7243 / ISO 7726 globe / Stull 2011 wet bulb; WBGT is not a DAG node). Scenario rasters never replace observed ones (`replace_covered`) and the dashboards read observed rows only (`_raster_stats_sql`). LST is not projected (it depends on surface reflectance) and SUHII stays observed. Land cover, soil, DSM or building changes after a run's SOLWEIG runs set `HeatInputChange`, and the run then asks to rerun its heat model. `RS_Imagery -> LST` and `LandCover -> LST` are implemented on demand by `urban_heat/lst/` (the map's LST tool, or `manage.py calculate_lst`): a Python port of Ermida et al.'s Statistical Mono-Window Earth Engine modules (`users/sofiaermida/landsat_smw_lst`) where Earth Engine only serves the inputs (Landsat 8/9 B10 TOA brightness temperature + L2 `QA_PIXEL`, ASTER GED, NCEP TPW) on a 30 m EPSG:28992 grid snapped to CrossTwin's NDVI layer (`LandCoverRaster`, `index=NDVI`), the equations run in numpy (`smw.py`), and the NDVI layer drives FVC → emissivity. Output is a `LandSurfaceTemperature` raster in °C. No receiver (a post_save must not start an Earth Engine download). Water vapour (`gee.TPW_SOURCES`, first source with a field on the scene's day): NCEP (`NCEP_RE/surface_wv`, what the original uses) stopped updating on 2026-03-18, so later scenes use ERA5 hourly (`total_column_water_vapour`, ~5 days behind real time; `smw.interpolate_tpw(step_ms=...)` takes each source's field spacing). The source is stored in `measurement_method`. A scene with no source for its day fails before the download with a clear message. `DSM -> SVF` is implemented on demand by `physicalEnv/calculations/svf.py::calculate_svf(bbox=|bbox_wgs84=, radius_m=...)` (the map's SVF tool or a shell call): RVT horizon search in numpy, heights divided by the cell size; it reads only the view plus a halo of one search radius (a window of `dsm_raster`, or of the DSM's COG warped back to the storage CRS at the COG's own cell size), crops the halo off and writes one `urban_heat.SkyViewFactor` row over the view (`source` = `DSM <id>: ...`). Windows above `MAX_CELLS` (16 M) are refused; a recalculation replaces that DSM's SVF rows inside the new view. No receiver. `DSM -> SVF -> Tmrt/PET`, `Meteorology -> Tmrt/PET/UTCI` and `Tmrt -> PET/UTCI` are implemented on demand by `urban_heat/solweig/` (the map's Thermal Comfort tool; `docs/THERMAL_COMFORT.md`): the view + `HALO_M` (50 m) read from the DSM with the editor's building patches, split into SOLWEIG's `Building_DSM`/`DEM`/`Trees`/`Landcover` (`inputs.py`), one hour of meteorology (manual, nearest KNMI station, ERA5; `met.py`) written as a two-row UMEP met file, `solweig-gpu` (PyTorch, CUDA when available) for walls, SVF (cached per input hash in `cogs/solweig_work/`), Tmrt and UTCI, then PET with the `pet-adjusted` package on the whole window before the halo is cropped (`pipeline.urban_pet` → `urban_pet_from_rasters`: Koopmans et al. 2020 urban heat island on the air temperature from the day's Tmax/Tmin/Kdown/wind — `Met` day fields, filled by the KNMI/ERA5 fetch — and 1.2 m wind from building/tree frontal areas; without day values or outside April–September no UHI; building cells nodata). It runs as a `ThermalComfortRun` in a background thread and stores one `MeanRadiantTemperature`, `UTCI` and `PET` row. No receiver. `Buildings -> DSM` is stored: see physicalEnv. `Buildings -> Canyon_Aspect` and `Streets -> Canyon_Aspect` are stored per street in `builtup.StreetCanyon` (see builtup); `Vegetation_Coverage -> DSM` is the editor's tree/forest overlay (see physicalEnv). `DSM -> PET` (2026-11-16, replaces `Canyon_Aspect -> Meteorology`): PET's urban heat island source areas (SVF, vegetation) and 1.2 m wind (building/tree frontal areas, Macdonald) are read off the same patched DSM window, so map edits reach PET on the next run; the stored street H/W is not used. Dashboard reads, not edges: `calculate_urban_morphology()` reads the stored canyons (length-weighted H/W, `calculate_canyon_aspect`) and `get_thermal_indices()` computes statistics over the stored rasters, Tmrt/PET/UTCI from one observed SOLWEIG run (`select_thermal_run`: most coverage of the unit, then latest hour) with the run and coverage shown on the card; no node consumes them, so no receiver. municipality effects; errors clustered by municipality, by PC4 area with one municipality), compares a linear and a log(1+score) form by AIC and spatially blocked cross-validation (a spline is a diagnostic only), tests the residuals with Moran's I (queen contiguity, 999 permutations, fixed seed) and fits a spatial error model when they fail, and stores the fit as `housing.PriceModel` (betas with and without controls, standard errors, R², n, WOZ year, network snapshot, Moran's I and p, library versions); `chain.modelled_price_per_sqm` = WOZ per m² × market factor × exp(k × Σ β × (T(A) − T(A₀))) is written to `builtup.Property.modelledPrice_EUR_per_sqm` (with `priceModel` and `priceMethod`; the observed `unitaryPrice_EUR_per_sqm` is untouched) by the receiver `accessibility_cascaded` on `accessibility_changed` and by the staff buttons "Fit price model" / "Reprice dwellings" on the housing dashboard; the market factor is the NVM price of the latest quarter over that of the quarter that ends on the WOZ valuation date (1 without both); what-if sliders (market change, accessibility effect × 0–2 with a conservative preset of 0.5, accessibility change in score points) recompute the card with the same function and write nothing. Every modelled price carries the label "association-based scenario (upper bound), not a forecast". Limits: a new NVM quarter or WOZ year reaches the stored prices at the next reprice or accessibility refresh (the DAG has no `Market_Reports -> Property` edge), a dwelling added later is priced at the next refresh that reaches its building, the spatial error model is fitted on the unweighted data and its coefficients re-estimated by weighted least squares on the filtered data, and the model is a cross-section (design `cross_section`; a within-neighborhood fit over time needs licensed listing data). Still open: amenities and the network follow how completely OpenStreetMap is mapped, a deleted OSM way is not removed on re-import, and a building added or moved afterwards is scored only by the next staff recompute or a nearby amenity/segment change (`DAG.dot` has no `Buildings -> Accessibility` edge; a deleted building takes its rows with it, CASCADE). `Zoning_Status -> Property`, `Property -> Mortgage` — none of `Property`/`Mortgage` have `save()` logic (`housing.HousePriceIndex` is the CBS national index 85773ENG, a stored input); the `calculations/indicators.py` functions only average pre-existing stored values. `HousingAffordability.save()` computes `affordabilityIndex` only from its own stored fields — it never pulls from `Mortgage`, `Rentals`, or watersupply tariff data, so `Rent/Mortgage/Water_Tariff_Afford -> Income_Expenses` and `Credit_Supply -> Mortgage` are unimplemented; `Income_Expenses -> Affordability_Stress` is partial and `Social_Profile -> Affordability_Stress` implemented (2026-11-24: `HousingAffordability.save()` derives the stress level from median income, rent/mortgage and the neighborhood's CBS socio-economic status). `NumberUsers -> Water_Tariff_Afford` — `UsersLocation` (the NumberUsers node) is now derived, but `MeteredResidential.userAffordability_PCT` is still a flat input.

**watersupply** — Climate scenario runs (2026-11-16): `ScenarioFreshWater` (per source of the run's unit: the `AvailableFreshWater` balance with the scenario's seasonal rain and yearly ET, `chain.scenario_water_balance`, also used by the dashboard's recharge card) and `ScenarioWaterSecurity` (demand, supply security and service time for the run's population year, variant and growth; production as today), receivers `climate_run_freshwater`, `climate_run_security`, `scenario_freshwater_saved`. A snapshot: never bulk-written (no deferral), flagged when a source is recomputed later, refreshed by *Recalculate* (re-save of the run). Implemented via `save()` + `watersupply/signals.py` (population cascade → `ConsumptionCapita` → `TotalWaterDemand` → `SupplySecurity`; `ExtractionWater`/`ImportedWater` → `TotalWaterProduction`, `OPEX`, `SupplySecurity`; `WaterTreatment`/`MeteredResidential`/`PipeNetwork` → `OPEX`; `PipeNetwork`/`UsersLocation` → `CoverageWaterSupply`; `NonRevenueWater` (real losses), `PipeNetwork`, `CoverageWaterSupply` (connections, editable pressure) → `LeakageIndex` (ILI with the IWA UARL)): `Supply_Security -> Service_Time` (same formula as `views._build_indicators`), `Imported_Water/WT_Cost/Network/Energy_Consumption -> OPEX` (`OPEX.save()` sums extraction `opex_EUR_m3 * current_extraction_Mm3_yr` (minus the well's `energy_EUR_m3` when it has pump energy data), pumping energy = pump kWh/day x 365 x `Energy.ElectricityCost.price(province, year)` (`chain.energy_cost_EUR_yr`; national row, then `DEFAULT_ELECTRICITY_EUR_KWH` 0.15 as fallback; receiver `electricity_changed` re-saves the year's OPEX and `TotalWaterProduction`), imported water, mean treatment `UnitaryOPEX_EUR_m3` of the year x volume, and pipe maintenance; `TotalWaterProduction`'s cost is not added, it would count the pump energy twice). `TotalWaterDemand`/`TotalWaterProduction` are stored in Mm³/day; `calculate_supply_security()` converts to m³/day. Demand = residential demand × `chain.SMALL_BUSINESS_DEMAND_FACTOR` (1.2, small businesses, Vitens; 2026-11-19, stored per `TotalWaterDemand.small_business_factor`). The population → consumption → demand → supply security → service time equations live once in `watersupply/calculations/chain.py`, used by both the models' `save()` and `views._build_indicators`: stored records use `chain.baseline_population(city, year)` (CBS median forecast of the record's year, no extra growth; current population without projections), saving/deleting a median `PopulationProjection` refreshes the city's chain via signal, and the population dock's what-if runs the same functions per request without writing, so the dashboard with default controls equals the stored chain. Consumption per capita of a year without its own record comes from `ConsumptionCapita.for_year(city, year)` (latest earlier year, else earliest later), used by `TotalWaterDemand.save()` and the dashboard (`_get_consumption_capita`, which shows e.g. "(2015 data)" next to the slider until it is moved); saving or deleting a record re-saves every `TotalWaterDemand` of its city. Extraction is allocated by watershed, not by well location: `calculate_total_extraction(unit)` gives each unit its population share (of each well's `ExtractionWater.volume_m3_d()`: measured yearly extraction, else flow x operation hours, else flow x 24 h; `TotalWaterProduction` uses the same expression) (neighborhoods assigned by point on surface; denominator = the larger of the stored neighborhoods' population and `Watershed.population_served`, the residents the watershed supplies, 2026-11-19, so a partly imported supply area no longer gets all the water; area share as fallback) of every watershed's active extraction, the watershed being the well's `source.watershed` or the `Watershed` containing it (wells with neither keep the old in-unit rule). So `SupplySecurity` of a city is refreshed when a well anywhere in its watershed changes, when a `Watershed`/`AvailableFreshWater` changes (all cities), and when another city of the same watershed changes population (`_refresh_watershed_neighbours`, deferred inside `deferred_water_refresh`). `Network -> Real_Losses`: each real `NonRevenueWater` record points via `pipe` (FK, `related_name='losses'`) to the `PipeNetwork` where the leakage is presumed — `clean()` requires it for real losses (`specificLoss` in `REAL_CHOICES`) and forbids it for apparent ones; the column stays nullable for older rows — and `calculate_nrw(year, adminBund)` adds `real_losses_by_pipe` (m³/day and m³/km/day, worst first). Per admin unit, each real loss counts in proportion to the share of its pipe's length inside the unit (`Length(Intersection(...))`, like the dashboard's network length — pipes run well → users location and can cross many units, so a leak is split, never duplicated; pipe-less legacy rows only appear network-wide), apparent losses are split by the unit's share of `UsersLocation.usersTotal` (`apparent_share`, None without user counts), and ILI is recomputed as CARL/UARL over the unit's real losses. Still unimplemented: `calculate_collection_ratio()` ignores `userAffordability_PCT` and acceptance rate despite its docstring; `calculate_opex_recovery()` computes directly from stored totals rather than calling `calculate_collection_ratio()` or referencing NRW; `calculate_water_quality()`'s `acceptance_rate` is `Avg('acceptanceRate')`, unrelated to computed compliance — so `Samples_WQ -> User_Acceptance_WS` is unimplemented; `WaterTreatment` has no `save()`, so `WT_Efficiency -> WT_Cost` is unimplemented; `calculate_supply_security()` sets a district/neighborhood's production share against its own demand (`chain.demand_m3_d` with its population and consumption; before 2026-11-19 it used the whole city's `TotalWaterDemand`); `SupplySecurity` for non-latest years is not refreshed by signals (OPEX/ExtractionWater/MeteredResidential/ImportedWater carry no year, so only the latest OPEX/SupplySecurity record is refreshed).
